What runs where: adopt only the step you need

Start with local hooks alone. Add a local hub on your machine when you want isolated previews and production approval gates, or connect a shared hub when your team joins.

Step 1 · No server

The ConfigHub plugin

Claude Code and Codex call a local program to record supported config edits and CLI changes in ~/.confighub/agent-changes. The next session can look up a setting and the request that changed it.

Step 2 · Local on 127.0.0.1

Local hub + cub

An optional 52 to 77 MB download running the ConfigHub server and bundled PostgreSQL as ordinary user processes in ~/.confighub/servers—no Docker, cluster, or account. Includes cub, ConfigHub’s CLI, for previews, staging vs. production copies, and approvals.

Step 3 · Team & hosts

Delivery & shared hub

Deliver approved production settings to Vercel, Fly, or AWS Parameter Store—or let Argo CD and Flux reconcile approved revisions—and move to an organization’s shared hub (on confighub.com or your own servers) with the exact same cub commands.

How one app’s setup becomes durable config for the next

A starter is a small YAML file of default settings and their reasons. Unlike a scaffolded repository template that goes stale the day you copy it, apps stay linked to their starter—so shared operational fixes carry forward while per-app overrides stay untouched.

  1. 1

    Connect your first app (shop)

    cub mini adopt shop creates shop-staging and shop-live (production) in the hub, filling in unset defaults from the web starter while keeping every value you already set in .env.production:

    starter: web
version: 1
# Some fields omitted.
defaults:
  - key: REPLICAS
    value: "2"
    reason: Two instances, so that one can restart without the service going down.

    What this file means: Every default setting carries a plain-English reason alongside its value so future agents and teammates know why it exists before changing it.

  2. 2

    Turn a hardening fix into starter version 2

    A teammate proposes warning-level logs and three instances with explicit reasons. The owner reviews and approves starter version 2 in the hub.

  3. 3

    The next app (cart) inherits the fix—and shop keeps its overrides

    When you build cart, it starts with version 2’s hardened defaults automatically. Upgrading shop applies the shared replica fix without overwriting shop’s custom production log level, and production still waits for owner approval.

Why Git, .env files, and static templates aren’t enough

Coding agents change settings across local files, cloud CLIs, staging, and production faster than anyone reads a diff. Durable config keeps the setup, its environment boundaries, and the reason behind every value.

ProblemGit + .env + copy-once templatesConfigHub durable config
Uncommitted edits & CLI flagsgit diff shows working changes. The diff alone doesn’t tell you what the agent was asked or which command changed a live setting.The plugin records supported edits and CLI changes with their prompts so a fresh session can explain them.
Staging vs. production safetyShared .env files or cloud logins let an agent overwrite production in the same turn as stagingAgent runs on a scoped key that updates preview/staging freely while production waits for your cub mini approve
Day-2 fixes across servicesTemplates are copied once on day one; rolling out a safer timeout across ten services means ten pull requestsApps stay linked to a versioned starter—shared fixes reach every app while app-specific overrides win
Answering “what runs where, and why?”Scattered across .env files, Helm values, Terraform vars, and hosting dashboardsThe hub records revisions and approvals. Check the running app or cluster to verify what reached it.
ConfigHub doesn’t replace your runtime or GitOps controller. Your hosting service (Vercel, Fly), VM, or Kubernetes cluster still runs your app, and Argo CD or Flux still reconciles your clusters. ConfigHub replaces the brittle templates and scattered config files above them.

Everyday commands and multi-agent guardrails

Everyday commands

  • In Claude Code (plugin only): /confighub:why LOG_LEVEL and /confighub:changes show every edit to a setting and what was asked.
  • In Terminal after Codex setup (plugin only): ~/.codex/confighub/bin/confighub mini changes prints the recorded edits and prompts for the current folder.
  • In your own Terminal (with a hub):
    • $ cub mini waiting — inspect pending production proposals, diffs, and each proposal’s ID (such as api-base/upload-...).
    • $ cub mini approve PROPOSAL_ID --note "Why" (or cub mini refuse) — approve or reject using the exact ID printed by cub mini waiting.
    • $ cub mini rollback APP-live --change-order PROPOSAL_ID --reason "Why" — propose an atomic rollback to the prior revision.

When agents run unattended or across a team

  • Scoped key per agent — can change staging and propose to production; cannot self-approve or read production secrets.
  • Exact-revision & concurrent proposals — multiple agents can propose in parallel without clobbering each other, and approving revision 3 never pre-approves revision 4.
  • Instant revocation — cub mini revoke-agent cuts off an agent on its next request.
  • Signed records & token tracking — verify entries and see token spend per change.
  • Laptop to shared hub — move to confighub.com or self-hosted servers when teammates and CI join (ConfigHub docs).

Approvals govern settings your app or delivery pipeline reads from the hub. An agent that also holds direct cloud or cluster write credentials can bypass the hub—see limiting what an agent can reach.

Free standalone local hub binary

The local hub package (52 to 77 MB for macOS and Linux) bundles the prebuilt ConfigHub server and PostgreSQL as a free single-machine binary—no account, license key, or network needed after download. Downloaded when you run /confighub:staging in Claude Code (or ~/.codex/confighub/bin/confighub mini get in Terminal), or installed standalone with SHA-256 checksums.

Also supports software shipped with a built-in hub. Machine-readable indexes for agents: AGENTS.md · llms.txt.
