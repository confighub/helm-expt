The problems ConfigHub solves

Your agent can build an app, and your host can deploy it. When you try a change, ConfigHub keeps track of which settings the preview uses, why they changed and what you approved for production.

1. Deploy your app cleanly

Your app’s settings, the checks they need before a deploy, and the add-ons they connect to are spread across .env files and your host’s dashboard.

ConfigHub: Saves base, staging, and live in one place, wires hosts and add-ons (Vercel, Fly, Heroku, Stripe, Supabase, Resend), and checks values before deploy.

Set up staging and production for your app →

2. Know why a setting changed

An agent edits .env without committing, and tomorrow nobody knows why a value is set that way.

ConfigHub: Keeps the request with supported edits, so a fresh chat still explains CACHE=on was “for Saturday’s sale” before you commit.

Try it in five minutes →

3. Reopen Friday’s live settings as a preview

Reproducing a bug or testing a new setting usually means touching the running app you already rely on.

ConfigHub: Runs Friday’s saved production settings in a separate local preview while your live app keeps serving untouched.

Open Friday’s settings as a preview →

4. Keep production behind your approval

One shared login lets an agent change production in the same turn as staging.

ConfigHub: Gives the agent a scoped key to tune staging on Vercel while production waits for your approval and rolls back cleanly.

Approve a change and see it live on Vercel →

5. Keep the proposal when you delete the sandbox

Disposable sandboxes disappear along with the tuning you just proved and why it worked.

ConfigHub: Brings the proposed setting and its reason back from Daytona for review while production stays untouched.

Try it with a Daytona sandbox →

6. Reuse a working setup on your next app

Copied templates drift, so hardening one service means repeating the same PR across ten apps.

ConfigHub: Links apps to a versioned starter so shared fixes roll out while each app keeps its own overrides.

ConfigHub doesn’t replace your runtime or GitOps controller. Your hosting service (Vercel, Fly, Unikraft, Daytona), VM, or Kubernetes cluster still runs your app, and Argo CD or Flux still reconciles your clusters. ConfigHub keeps the settings, reasons, previews, and approval gates above them.

How one app’s setup becomes durable config for the next

A starter is a small YAML file of default settings and their reasons. Unlike a scaffolded repository template that goes stale the day you copy it, apps stay linked to their starter—so shared operational fixes carry forward while per-app overrides stay untouched.

  1. 1

    Connect your first app (shop)

    cub mini adopt shop creates shop-staging and shop-live (production) in the hub, filling in unset defaults from the web starter while keeping every value you already set in .env.production:

    starter: web
version: 1
# Some fields omitted.
defaults:
  - key: REPLICAS
    value: "2"
    reason: Two instances, so that one can restart without the service going down.

    What this file means: Every default setting carries a plain-English reason alongside its value so future agents and teammates know why it exists before changing it.

  2. 2

    Turn a hardening fix into starter version 2

    A teammate proposes warning-level logs and three instances with explicit reasons. The owner reviews and approves starter version 2 in the hub.

  3. 3

    The next app (cart) inherits the fix—and shop keeps its overrides

    When you build cart, it starts with version 2’s hardened defaults automatically. Upgrading shop applies the shared replica fix without overwriting shop’s custom production log level, and production still waits for owner approval.

Everyday commands and multi-agent guardrails

Everyday commands

  • In Claude Code (plugin only): /confighub:why LOG_LEVEL and /confighub:changes show every edit to a setting and what was asked.
  • In Terminal after Codex setup (plugin only): ~/.codex/confighub/bin/confighub mini changes prints the recorded edits and prompts for the current folder.
  • In your own Terminal (with a hub):
    • $ cub mini waiting shows each production change that waits for you, with what it would change.
    • $ cub mini approve APP approves the change waiting for that app. When the app is linked to Vercel or Fly, the same command puts it live there. cub mini refuse APP --reason "Why" turns it down, and the agent can read your reason.
    • $ cub mini rollback APP --reason "Why" proposes undoing the last approved change. It waits for your approval like any other.

When agents run unattended or across a team

  • Scoped key per agent — can change staging and propose to production; cannot self-approve or read production secrets.
  • Exact-revision & concurrent proposals — multiple agents can propose in parallel without clobbering each other, and approving revision 3 never pre-approves revision 4.
  • Instant revocation — cub mini revoke-agent cuts off an agent on its next request.
  • Signed records & token tracking — verify entries and see token spend per change.
  • Laptop to shared hub — move to confighub.com or self-hosted servers when teammates and CI join (ConfigHub docs).

Approvals govern settings your app or delivery pipeline reads from the hub. On the same machine, an agent with shell access or direct cloud/cluster credentials can still reach your local sign-ins—see limiting what an agent can reach.
