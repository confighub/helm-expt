ConfigHub for apps made with AI

Your agent makes your apps. Durable config makes the platform.

Ask a coding agent for an app and it writes the app, with a staging and a production setup. ConfigHub keeps that setup as durable config: every setting with its reason, kept through the next session, the next version and the next app. Kept that way, the setup of your apps is your platform.

Install the plugin

claude plugin marketplace add confighubai/confighub-mini-plugin
claude plugin install confighub@confighub

The plugin works alone, with no hub. Ask Claude Code to change a setting, then run /confighub:why SETTING to see the recorded change and the reason for it.

Want staging and production too? In an empty Git repository, ask Claude Code:

Build me a small web service using ConfigHub, with a staging and a production setup.

The free local hub runs on macOS and Linux without a ConfigHub account, Docker or Kubernetes. Connecting an app you already have reads its settings files without rewriting them. If you are an AI agent, start with AGENTS.md and llms.txt.

Why this, and why now

  1. 1

    People make and run apps by asking agents

    An agent changes settings many times a day, across staging, production and every customer's copy. That is faster than anyone reads a diff.

  2. 2

    So the platform has to come from somewhere else

    Staging, production, promotion, rollback and limits used to come from a platform team or a hosting service. An agent can now write all of that in the same request as the app. But it lands in scattered files, the next session overwrites it, and every new app starts from nothing.

  3. 3

    ConfigHub keeps the setup, its changes and their context

    It keeps the setup itself, wherever the app runs, with every change to it and the context for each change: what was asked, and why. That is what durable means. What you and your agents decided is still there for:

    • the next session, which starts from what was set and why
    • the next agent, which is told before it undoes a value
    • the next version, which keeps your own values
    • the next environment, which takes exactly what you approved
    • the next app, which starts from the first

An example: two apps from one setup

A developer builds a web shop with an agent. The next app is a cart service, which can start from the setup the shop already uses.

  1. 1

    The first app gets a setup

    cub mini adopt shop gives the shop a staging and a production copy, using the web starter for settings the developer has left open:

    starter: web
version: 1
# Some fields omitted.
defaults:
  - key: REPLICAS
    value: "2"
    reason: Two instances, so that one can restart without the service going down.
  2. 2

    A fix to the first app becomes part of the setup

    A teammate proposes a new starter version that uses warning-level logs and keeps three instances running. They give a reason for each setting. The owner reviews and approves the starter version.

  3. 3

    The second app starts with the fix, and the first keeps its own values

    The cart service starts with the new defaults. The shop takes the same update while keeping its own production log level. Production changes still go through their own approval.

Platforms were built before the apps. Agents build the app first.

Platform engineering builds a platform and fits apps to it. Durable config starts with the app and keeps what the agent set up for it, so the platform grows out of the apps.

Platform engineering as we know itDurable config
What comes firstThe platform, built by a team ahead of the appsThe app. Its setup becomes the base for the next one
How an app gets its setupA template, copied once when the app is createdA starter the app stays linked to

ConfigHub doesn't run your app. Your cluster, hosting service or VM still does, and Argo CD and Flux still deliver to your clusters. It replaces the templates, the portal and the scattered settings files above them.

Five ways it is better

  1. 1

    Nothing to build first

    Start with an app. Its staging and production setup can become the starting point for the next app.

  2. 2

    Templates that keep working after day one

    A scaffolded app is a copy made once, so the template's next version never reaches it. Here a starter's next version reaches every app made from it, and each app keeps its own values and reasons. Starters

  3. 3

    The reason travels with the value For agents

    An agent can't ask the platform team why a limit is set as it is. Without the reason it "fixes" the value, and the next agent fixes it back. With the record, the next agent can see why a value was chosen before changing it. What the plugin records

  4. 4

    Guardrails that hold against agents For agents

    Give agents a way to test changes and give the owner a separate decision about production:

    • a key of their own
    • a staging copy they can change at once
    • a line they cannot cross

    The hub refuses an agent's own approval, and it is small enough to sit in every sandbox. Agent keys

  5. 5

    Configuration you can query and build on

    Platform stacks are a template language for each tool: Helm for clusters, Terraform for cloud, env files for hosting services. A change across the fleet is many pull requests. As data, "which version runs where" is one question, and one change is read across all apps, wherever they run. Tools are built on data, not on templates.

Day to day, and when agents do real work

Everyday commands

  • /confighub:why LOG_LEVEL shows every change to a setting, and what was asked each time.
  • cub mini waiting shows what waits for you. Approve or refuse it by the name it shows.
  • To roll back, ask the agent to put the old value back, then approve it.

Control over your agents

  • A key for each agent, with only the rights it needs.
  • Approval of the exact change, and nothing after it.
  • A way to stop them at their next request.
  • Signed records you can verify.
  • What it cost, in tokens, for supported sessions.

This covers what your app reads from the hub. An agent that also holds your cloud or cluster credentials can still go around it. See limiting what an agent can reach.

From your laptop to your team

A local hub runs on your own machine, free and with no account. A shared hub, on confighub.com or on your own servers, gives your team, your agents and your CI jobs one place, with the same commands.
