ConfigHub for coding agents

Ship faster with coding agents. You decide what reaches production.

ConfigHub is a small server, called a hub, that holds your app's settings. Your agents can change the staging settings whenever they like, but nothing changes in production until you say yes. And every change comes with a note on why it was made.

You can run the hub on your laptop, or share one with your team. The easiest way in is the ConfigHub plugin for Claude Code: ask for an app "using ConfigHub" and it sets up a hub for you. It works with Codex too.

Your agent shouldn't be able to change production by itself

Your app is slow, so you ask your agent to "turn on debug logging so we can see what's going on."

Without ConfigHub. Say staging and production both read the same .env file. The agent changes the log level there and tells you it's done. Neither of you realizes production reads that file too. Production starts logging every request in full, customers' email addresses included, and you find out weeks later.

With ConfigHub. Staging and production get their settings from the hub, and the agent has its own key that can't approve anything for production. The agent makes the same edit. This time:

  1. Staging gets debug logging right away, so you can start digging.
  2. Production stays as it is. The agent tells you there's a production change waiting for you.
  3. You run cub mini waiting (cub is ConfigHub's command-line tool) and see LOG_LEVEL=info → LOG_LEVEL=debug.
  4. You say no, with a reason: "Debug logs leak customer emails." Production keeps its normal logging.
  5. The next agent that tries the same change is told you already said no, and why.

This covers what your app reads from the hub. If your agent also has your cloud or cluster credentials, it can still go around it. See limiting what an agent can reach.

How it works

1. Install the plugin

From the first session it keeps track of what your agents change and why. You don't need a hub yet.

2. Ask for an app

Say "using ConfigHub" in your request. The agent writes the app and starts a hub on your laptop, with staging and production settings.

3. Approve what goes live

Agents change staging. Anything for production waits until you approve it.

Already have an app? If its settings live in .env.staging and .env.production, Terraform var files, or a Kustomize repo that Argo CD or Flux deploys, just ask the agent to "attach ConfigHub to this app". It won't touch your files. Use it with an app you have

Get started

claude plugin marketplace add confighubai/confighub-mini-plugin
claude plugin install confighub@confighub

Then, in an empty folder, ask Claude Code:

Build me a small web service using ConfigHub, with a staging and a production setup.

Works on macOS and Linux. To remove it, run cub mini uninstall --delete-data. Your app's files are never touched.

Step-by-step walkthroughs What happens, and why

Everyday commands

  • /confighub:why LOG_LEVEL in Claude Code shows every change to a setting, and what was asked for each time.
  • cub mini waiting shows what's waiting for you. cub mini approve or cub mini refuse decides it.
  • To roll back, ask the agent to put the old value back, then approve it.
  • When a Helm chart you use has a new version, you can upgrade and keep your own values.

An example: a small web shop

A team runs a web shop made of two services, a storefront and an orders service. Nadia builds them with an agent. Ravi looks after production. One hub keeps the settings of both, with a staging copy and a production copy of each.

  1. 1

    The team writes its defaults once

    A starter is a small YAML file with the settings every service of one kind starts with, each with a note on why. It is the same idea as Spring Boot starters, for any kind of app. The shop's starter adds two settings to the ones every small web service gets:

    starter: shop-service
version: 1
after: [web]
defaults:
  - key: SHOP_CACHE_SECONDS
    value: "60"
    reason: Pages are cached for a minute, so a change to a price is seen within a minute.
  - key: SHOP_TIMEOUT_SECONDS
    value: "10"
    reason: A request stops after ten seconds, so a slow payment provider cannot hold every worker.

    Ravi keeps the starter in the hub. A new version counts only once he approves it.

  2. 2

    Nadia connects the storefront with one command

    cub mini adopt storefront gives the storefront the team's settings, each with its reason. Her own values stay: she set a 30-second cache for production during sales, and the starter leaves it alone. Nothing reaches production until she approves it.

  3. 3

    An agent's change to production waits

    Her agent turns on debug logging. Staging gets it at once. Production waits, and she says no, with the reason the next agent is told.

  4. 4

    Ravi fixes production once, for every service

    He sets a request size limit and a rate limit on the storefront's production copy, each with his reason. Then he adds both to the starter as version 2, and approves it.

  5. 5

    The next service starts with the fixes

    The orders service connects with version 2 and gets Ravi's limits, with his reasons. Nobody types them again. The storefront takes version 2 too, and keeps its own values. Its production copy changes only with an approval.

Both services run on Vercel. Here a local stand-in answers as Vercel would, so you need no Vercel account. The walkthrough Alice ships it, Bob hardens it runs the same loop on your laptop, with every command.

  • Your values win. A value you set is never replaced by a starter.
  • It writes once, when the app is connected or takes a new version. After that the values are yours.
  • Fix a default once and every new app gets the fix.
  • No code. One command checks a starter before anyone uses it.

confighub mini comes with starters for a small web service and for a Kustomize repository that Argo CD or Flux deploys. Starters for apps on Vercel and apps that read AWS Parameter Store are new: Parameter Store delivers to a real AWS account you sign in to, or to a stand-in with no account, and Vercel delivers to its stand-in for now. A starter for experiments in a Daytona sandbox can be tried on your computer first. Starters are off until one setting turns them on. The guide to starters shows how to turn them on, keep them in your hub, and write your own.

When agents do real work

Once agents run for hours, or several of them share an app, you'll want more control. A hub gives you:

A key for each agent

Every agent gets its own key and only the rights it needs. It can suggest a production change, but it can't approve one. Agent keys

Approval of the exact change

You approve one specific change. Anything that comes after it needs its own approval. Approvals

A way to stop them

Take away one agent's access, or shut the hub down. The agent is cut off at its next request. Stopping agents

A record nobody can quietly edit

Every change is signed when it's recorded. One command tells you if anything was edited, added or deleted later. Signed records

Agents asking each other

When one agent asks another for a change, the hub records who asked, so you always know where a change came from. Requests between agents

What it cost

Every change shows how many tokens the agent spent making it. Model use
