Start in five minutes with one uncommitted setting—zero servers, zero accounts. Add the local hub in Exercise 2 when you want an isolated preview, Friday’s saved settings, or a second app that inherits your working defaults.

Terminal

01 · Plugin only · Zero servers, zero accounts

Find out why a setting changed, a session later

Git shows the edit after you commit. The plugin keeps the request with supported edits in ~/.confighub right away, so a fresh chat can tell you why the cache is on before you undo it.

You ask for one uncommitted change, then open a fresh session in the same folder. Your agent makes the edit and later explains it from the local record.

  1. Use your own Git app, or create a sample folder with one setting and start claudecodex.

    Terminal 
    mkdir try-confighub && cd try-confighub && git init -q &&
  printf 'CACHE=off\n' > .env && git add -f .env

    In your own app, open a fresh session and pick any non-secret setting you want to change with a reason.

  2. Ask in Session 1 (and allow the edit):

    Ask your agent 
    Set CACHE=on in .env for Saturday’s sale. Leave it uncommitted.

  3. Open a fresh session in the same folder and ask:

    Ask in a fresh session 
    Why is the cache on?

    You can also inspect the record directly in Claude Code with /confighub:why CACHE.

    You can also inspect the record in Terminal with ~/.codex/confighub/bin/confighub mini changes.

What you should see

.env · recorded by ConfigHub plugin CACHE: off → on asked: "Set CACHE=on in .env for Saturday’s sale. Leave it uncommitted."

Look for both the previous value (off) and Saturday’s sale. The second session recovers both before you commit anything.

Clean up anytime by deleting try-confighub.

02 · Local hub (cub mini) · Safe previews & saved settings

Try a change in a running preview before shipping it

Testing a setting or reproducing a bug usually means touching the running app you already rely on. With the local hub, previews run on their own settings and tomorrow’s chat still knows where to find them.

What’s added in Exercises 2 & 3: Your agent downloads cub mini on first use (a free local ConfigHub server + PostgreSQL on 127.0.0.1 only—no Docker, no account). It adds isolated previews, base / staging / live copies, and scoped agent keys.

  1. Start from a new folder or attach your app:

    In a new Git folder (mkdir greeter && cd greeter && git init -q), ask:

    Ask your agent 
    Build a small greeting app using ConfigHub. Give it a configurable greeting and run it locally.

    In a local Node HTTP app (node server.js on 127.0.0.1 reading .env), ask:

    Ask in your existing app 
    Show me my app as it is and a local preview with the heading “Evening collection.” Give me both links and keep the preview running for tomorrow.

    Say yes to local setup. Your agent downloads mini on first use and shows both links—go straight to Step 3.

  2. For the new app, reopen Claude Code in the same folder (Step 1 wrote .claude/settings.local.json so sessions run on the app’s scoped agent key) and ask:

    For the new app, open its scoped session using the run-codex command printed at the end of Step 1, then ask:

    Ask your agent 
    Try a warmer greeting in preview.

  3. Open the local URL your agent returns. Close the chat, open a fresh session in the same folder, and ask:

    Ask in a later session 
    Where’s the preview I left running? What does it serve?

    A fresh session finds the running preview address and process without being given the URL. Ask your agent to stop the preview when you finish.

From the recorded greeter run

Your wording may differ. The preview leaves your repo files, staging, and production untouched.

03 · Multi-app inheritance · Keep per-app overrides

Give a second app the greeting you just tried

A copied template gives you today’s settings. With mini, the new app stays linked to shared defaults. A later fix can reach both apps while each keeps its own values.

You choose the greeting to share and open a new Git folder. Your agent runs both apps with their staging settings and checks that the second app inherited the greeting.

  1. In the greeter session from the preview exercise, ask:

    Ask your agent 
    Make the preview greeting our shared default for welcoming visitors. Put it in staging and show me what the greeter serves there.

  2. In Terminal, start from the folder that contains the greeter repository. Create a sibling folder:

    Terminal 
    mkdir catalog && cd catalog && git init -q

    Open a new claude session here.

    Open a new codex session here using your ordinary login. The greeter’s launcher is scoped to the first app.

  3. Use the first app’s name in your request. Reopen with the catalog’s own launcher if setup asks you to.

    Ask your agent 
    Build a small catalog service using greeter’s ConfigHub setup. Let it inherit the greeting. Run catalog with its staging settings and show me the response.

What to check

Both staging apps should serve the greeting you chose. Ask your agent to show where catalog gets it. In the recorded run, catalog served Welcome to the neighborhood! with no greeting in its own settings file.

Catalog has its own production approval. In the two-app shop example, changing the shared hours once gave both apps daily support while the shop kept its coral banner and the cart kept indigo.

Vercel · Try a shorter cache for a sale
Ask your agent
Prices change more often during the sale. Try a 30-second price cache in a Vercel preview. Show me the cache headers from the preview and the live shop. Leave the production change for me to approve.

Vercel runs the preview. Mini keeps the proposed value and reason, and its delivery add-on checks your approval. In the sale example, the preview served a 30-second cache header while the live shop still served 60. Vercel guide

Daytona · Keep the experiment after deleting the sandbox
Ask your agent
The queue spiked. In a disposable Daytona sandbox, run the same jobs at 120 and 240 per batch. Show me the difference and save the change and its reason for review before you delete the sandbox.

Daytona runs the job. Mini lets you bring the setting and its reason home for review. After the test sandbox was deleted, a new hub held the proposal with 240 in staging and 120 in its production settings. Daytona guide

Unikraft · Rehearse an incident notice
Ask your agent
Checkout is delayed. Show me our incident notice on Unikraft staging using the same image as production. Read both notices back to me. I’ll decide whether to publish it.

Unikraft can run two instances on one image. Mini keeps the proposed notice behind owner approval on its delivery path. In the example, staging warned of a checkout delay while production still said “Orders ship as usual.” Unikraft guide

When your team joins

Earlier revisions and delivery stay on the original hub (moving to a shared hub). Teammates and CI then approve changes as named owners and manage one base across ten services.
