01 · Plugin only

Find out why the cache is on

Why it matters. A settings file tells tomorrow’s agent that caching is on. The plugin can also show the request that turned it on, even if nobody committed the edit.

You set up the plugin and sample Git folder in the five-minute guide. Ask “Turn the cache on for next week’s sale. Don’t commit.” Open a fresh session in the same folder and ask “Why is the cache on?”

Your agent changes CACHE in the first session. In the second it reads the record and explains the change.

What to look for

The change from off to on and the request about the sale. No hub or ConfigHub account needed.

You can also inspect the record yourself. In Claude Code, type /confighub:why CACHE. In Codex, use the record command.

Compare with and without the plugin in a test where a deploy would undo an earlier change. You can also see which alternatives the agent considered when it chose two replicas.

02 · Your first app on a local hub

See a change before you ship it

Why it matters. A preview gives your agent somewhere to experiment. You can judge the result from the running app, and decide later what production gets.

You open a local Node app and ask your agent to attach it. In Codex, open the app session using the command setup prints. Ask “Try a warmer greeting in preview.” Open the address you get back. Try the preview in your app.

Your agent changes the preview setting, starts the app and checks what it serves. Reopen the app session and ask “What’s my preview showing?” Your agent looks up the running preview.

What the running apps returned

Preview: Welcome to the neighborhood!
Staging and production: Hello, world!

These were local processes on one Mac. A stored setting alone doesn’t show that an app has loaded it.

Want to keep the greeting? Ask your agent to make it the shared default. You review the production change. In the second-app example, a catalog in another folder inherited the greeting and had its own production approval.

03 · A starter for more than one app

Give the next app the logging fix

Why it matters. The shop needs 20 database connections. Other apps don’t. They should all use the safer logging default. A starter holds shared defaults and the reasons for them. Approving a new version lets you improve existing apps as well as new ones.

You follow steps 1–3 in Harden the shop to set up the owner and agent roles. Give your agent the hardening request. Review the shop rollout and the shared starter separately. You can leave either pending.

Your agent proposes the shop changes and a new starter version. After your decisions, it starts the cart from the approved starter and checks which settings the shop kept.

What to check in the hub

The cart gets the new logging and replica defaults. The shared starter does not acquire the shop’s pool size. The shop keeps its production log-level override.

This story checks stored settings. For a running-service comparison, see two apps on Fly.

What does mini add to ConfigHub?

The plugin captures the edit and request in the coding session. The local hub is ConfigHub on your machine; cub mini arranges its usual variants, permissions and change orders for a common job. To see what it saves you setting up by hand, compare mini and plain cub, command by command.

In an Argo CD setup comparison, agents using plain cub often switched delivery before the approval gate was in place. Agents using mini more often got the order right. That’s a difference in setup; the test didn’t show an unapproved change reaching production. Read the eleven-check comparison.

When a colleague or CI needs the same settings, move to a shared hub. Follow Story 24: one base for ten apps to see how one shared update can preserve each app’s own values. In the Slack approval example, a message saying “the owner approved” still leaves the order pending for its named owner.

Two things to try next

Restart a Temporal worker halfway through a rollout

You choose the disposable Temporal worker rehearsal and ask “Show me what happens if the worker restarts while a retry change is waiting.” It needs Go, Python 3 and the Temporal CLI.

Your agent runs the packaged rehearsal and shows you the probe results. The rehearsal supplies its own test approval. In your own rollout, you approve the production change.

Look for the old retry limit after restart, one attempt after approval, and a refusal if the policy differs from what was approved.

Find out why a running cluster disagrees with Git

You choose the disposable local cluster in Git, the hub and what’s running. Give the quick-start request to your agent. Decide when you’re finished inspecting the cluster and want it removed.

Your agent runs the example, compares the three replica counts, finds the extra environment variable and shows you the return to Git.

Look for two replicas in Git, three in the hub with a reason, and four on the cluster. The extra variable appears only on the cluster.
