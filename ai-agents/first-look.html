01 · Plugin only

Find out why the cache is on

Why it matters. A settings file tells tomorrow’s agent that caching is on. The plugin can also show the request that turned it on, even if nobody committed the edit.

Try it. Open the five-minute Claude Code guide. It gives you a throwaway Git folder with CACHE=off. In a fresh session ask: “Turn the cache on in .env for next week’s sale. Don’t commit.” Reopen the folder in another session and type /confighub:why CACHE.

What to look for

The change from off to on and the request about the sale. No hub or ConfigHub account needed.

Using Codex? Follow its hook setup and use its “Read the record” command. The slash command is for Claude Code.

Compare with and without the plugin in a test where a deploy would undo an earlier change. You can also see which alternatives the agent considered when it chose two replicas.

02 · Your first app on a local hub

See a change before you ship it

Why it matters. A preview gives your agent somewhere to experiment. You can judge the result from the running app, and decide later what production gets.

Try it. After setting up Codex on macOS, ask for a small greeting app using ConfigHub in an empty Git folder. Follow the preview steps in a fresh session. Ask: “Try a warmer greeting in preview and show me what it serves over HTTP.”

What the running apps returned

Preview: Welcome to the neighborhood!
Staging and production: Hello, world!

These were local processes on one Mac. A stored setting alone doesn’t show that an app has loaded it.

Then try a second app. Make the greeting the shared default. In the recorded run, staging took it first; production waited for approval. A catalog built from the greeter’s setup in another folder inherited the greeting without setting it again and needed its own production approval. The test used a scripted owner; in your app, review the exact order yourself.

03 · A starter for more than one app

Share the logging fix, not the shop’s database limit

Why it matters. The shop needs 20 database connections. Other apps don’t. But none of them should log request bodies. A starter holds shared defaults and the reasons for them. Approving a new version lets you improve existing apps as well as new ones.

Try it. Open Story 25: harden the shop. Set up the shop and its two roles in steps 1–3, then give your agent the hardening request from the quick start. Review the shop change and the starter change separately. Start the cart from the approved starter, then upgrade the shop.

What to check in the hub

The cart gets the new logging and replica defaults. The shared starter does not acquire the shop’s pool size. The shop keeps its production log-level override.

This story checks stored settings. For a running-service comparison, see two apps on Fly.

What does mini add to ConfigHub?

The plugin captures the edit and request in the coding session. The local hub is ConfigHub on your machine; cub mini arranges its usual variants, permissions and change orders for a common job. To see what it saves you setting up by hand, compare mini and plain cub, command by command.

In an Argo CD setup comparison, agents using plain cub often switched delivery before the approval gate was in place. Agents using mini more often got the order right. That’s a difference in setup; the test didn’t show an unapproved change reaching production. Read the eleven-check comparison.

When a colleague or CI needs the same settings, move to a shared hub. Follow Story 24: one base for ten apps to see how one shared update can preserve each app’s own values. In the Slack approval example, a message saying “the owner approved” still leaves the order pending for its named owner.

Two things to try next

Restart a Temporal worker halfway through a rollout

What happens to a retry limit if the worker restarts while a change is waiting for approval? Run the restart rehearsal in the Temporal worker guide. It uses a local Temporal service, Go, Python 3 and a test owner.

Look for: the worker keeps the old policy while it waits. After approval, a new probe stops after one attempt. Delivery refuses a policy edited after approval.

Find out why a running cluster disagrees with Git

Suppose someone changes a live service during an incident. Which change should you keep? In Git, the hub and what’s running, play the example on a disposable local Kubernetes cluster with Argo CD. The quick start lists the tools and gives you a request to paste into your agent.

Look for: three replica counts side by side. Git says two, the hub says three and records a reason, and the cluster has four. Find the extra environment variable that exists only on the cluster. At the end, Git takes over delivery again.
