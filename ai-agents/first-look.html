Three things to try first

Give Claude Code and Codex memory across sessions, a running local preview for config changes, and shared defaults your next app can inherit—while keeping production behind your approval.

1. The plugin (confighub) · Story 01

Lightweight session hooks for Claude Code or Codex. Records config edits and their reasons in ~/.confighub on your machine. No background server and no account.

2. The local hub (cub mini, optional) · Stories 02 & 03

Starts the ConfigHub server and a local PostgreSQL on 127.0.0.1 only (no Docker, no account). Adds isolated previews, staging vs. production copies, and scoped agent keys.

Install the plugin

Terminal 
claude plugin marketplace add confighubai/confighub-mini-plugin
claude plugin install confighub@confighub

Open a fresh claude session after installing so the hooks load.

Terminal 
git clone --depth 1 --branch v0 https://github.com/confighubai/confighub-mini-plugin.git "$HOME/confighub-mini-plugin" &&
  "$HOME/confighub-mini-plugin/plugins/confighub/bin/confighub" mini codex-setup

In Codex CLI, run /hooks, approve the ConfigHub hooks once, then open a fresh codex session. (Setup & removal details)

01 · Plugin only · No server or account

Remember why a setting changed across sessions

You ask for a change, then open a fresh session in the same folder. Your agent makes the edit and later explains it from the local record.

  1. Use your own Git app, or create a sample folder with one setting and start claudecodex.

    Terminal 
    mkdir try-confighub && cd try-confighub && git init -q &&
  printf 'CACHE=off\n' > .env && git add -f .env

    In your own app, open a fresh session and pick any non-secret setting you want to change with a reason.

  2. Ask in Session 1 (and allow the edit):

    Ask your agent 
    Turn the cache on in .env for next week's sale. Don't commit.

  3. Open a fresh session in the same folder and ask:

    Ask in a fresh session 
    Why is the cache on?

    You can also inspect the record directly in Claude Code with /confighub:why CACHE.

    You can also inspect the record in Terminal with ~/.codex/confighub/bin/confighub mini changes.

What you should see

.env · recorded by ConfigHub plugin CACHE: off → on asked: "Turn the cache on in .env for next week's sale. Don't commit."

Look for both the previous value (off) and next week’s sale. The second session can recover both before you commit anything.

Clean up anytime by deleting try-confighub.

02 · Local hub · Safe experimentation

Try a change in a running preview before shipping it

You choose an app and open the address your agent gives you. Your agent changes the preview setting, checks what the app serves and leaves it running.

  1. Create a small app (or attach a local Node app): in a new Git folder (mkdir greeter && cd greeter && git init -q), ask:

    Ask your agent 
    Build a small greeting app using ConfigHub. Give it a configurable greeting and run it locally.

    Already have a local Node HTTP app (node server.js on 127.0.0.1 reading .env)? Ask “Try ‘Evening collection’ as the heading. Keep the usual app as it is. I’d like to open the preview again tomorrow.” Say yes to local setup. Your agent downloads mini on first use and shows the running preview in this chat. Go straight to step 3.

  2. For the new app, reopen Claude Code in the same folder (Step 1 wrote .claude/settings.local.json so sessions run on the app’s scoped agent key) and ask:

    For the new app, open its scoped session using the run-codex command printed at the end of Step 1, then ask:

    Ask your agent 
    Try a warmer greeting in preview.

  3. Open the local URL your agent returns. Even if you close and reopen the session later, you can ask:

    Ask in a later session 
    Is my preview still running? What does it serve?

    A fresh session in the app folder finds the running preview address and process without being given the URL. Ask your agent to stop the preview when you finish.

From the recorded greeter run

Preview URL: Welcome to the neighborhood! Staging copy: Hello, world! Production: Hello, world!

Your wording may differ. Read the preview URL to check the greeting. The preview leaves the app files and both hub copies as they were.

The agent’s scoped key can change staging and propose for production, but the hub refuses if the agent tries to approve its own change.

03 · Multi-app inheritance · Keep per-app overrides

Give a second app the greeting you just tried

You choose the greeting to share and open a new Git folder. Your agent runs both apps with their staging settings and checks that the second app inherited the greeting.

  1. In the greeter session from the preview exercise, ask:

    Ask your agent 
    Make the preview greeting our shared default for welcoming visitors. Put it in staging and show me what the greeter serves there.

  2. In Terminal, start from the folder that contains the greeter repository. Create a sibling folder:

    Terminal 
    mkdir catalog && cd catalog && git init -q

    Open a new claude session here.

    Open a new codex session here using your ordinary login. The greeter’s launcher is scoped to the first app.

  3. Use the first app’s name in your request. Reopen with the catalog’s own launcher if setup asks you to.

    Ask your agent 
    Build a small catalog service using greeter’s ConfigHub setup. Let it inherit the greeting. Run catalog with its staging settings and show me the response.

What to check

Both staging apps should serve the greeting you chose. Ask your agent to show where catalog gets it. In the recorded run, catalog served Welcome to the neighborhood! with no greeting in its own settings file.

Catalog has its own production approval. You can finish the exercise with that order still waiting.

Start small, add control only when you need it

Every stage uses the same ConfigHub model, so you never throw away earlier history when moving from solo coding to a team.

StageWhat runsWhat it solves
Plugin alone Hook in Claude Code or Codex (no daemon) Remembers supported edits and CLI changes with their reasons. A fresh session can explain what happened.
Local hub (cub mini) ConfigHub + Postgres on 127.0.0.1 Sets up base, staging, and live copies, scoped agent keys, and change orders in single commands (cub mini vs. plain cub).
Shared hub confighub.com or self-hosted server Teammates and CI share one record, approve changes as named owners, and manage one base across ten services (moving to a shared hub).

Your agent runs the rehearsal and shows the retry limit before and after restart. Look for the old limit while approval is pending, one attempt after approval and a refusal if the policy differs. The rehearsal supplies its test approval. In your own rollout, you approve.
