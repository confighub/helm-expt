## What this found

1. **One generic workflow ran this plan.** The workflow code names no chart and
   no object. The two gates, the two apply stages and the eleven lifecycle
   stages all came from the bundle.
2. **The lifecycle stages carry names, not actions.** The runner works because
   it knows ten stage names from the recorded run, such as
   `controller-manager-ready`, and maps each to an action and a bundle object.
   A plan document with an `action` and a `target` field per stage would let a
   runner work without that list.
3. **Two documents describe the apply.** The apply-ordering document and the
   first three lifecycle stages both say how the objects were applied. The
   runner follows the apply-ordering document and records those three stages
   as done by it. One source would remove the choice.
4. **The recorded plan steps can only be approvals.** Their `checks` are
   sentences, so the runner turns each into a gate a person approves. To run
   one, the step needs a check a machine can carry out.
5. **The objects travel through the history.** Reading the plan put about
   514 KB into the history, which reached 1.1 MB. A bundle with 125 objects
   would be several times that. The next version should pass step names to the
   workflow and let each activity read the objects from the bundle.
