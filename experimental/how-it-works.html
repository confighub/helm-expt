How it works

Helm rebuilds your whole config from templates every time, so any change you made by hand is wiped on the next upgrade. We render the chart once into plain files, let you change anything afterward, and put your change back on every upgrade. This page is the whole model: the catalog, the decisions behind it, the patterns we recommend, the choices that stay yours, and exactly how every claim is verified.

1 · The core idea

Helm: rebuilt from templates

  • Every setting has to be wired into the template up front.
  • Need a setting the chart didn't expose? You're stuck, or you copy the whole chart.
  • helm upgrade rebuilds from the templates and overwrites what you changed.

Us: kept as files you can edit

  • Render once to plain YAML files you can read.
  • Change any field afterward — by hand, a script, or an AI agent.
  • The next upgrade keeps your change instead of wiping it.

3 · The lifecycle: recipe → render → record → route → change

This is how a chart becomes something you can install, trust, and change. Five steps, each named for what it does. (The small codes are the catalog's own labels, if you read the matrix.)

RECIPEF1 · source

The recipe — your source of truth

A recipe is the chart and version, the values you chose, the base you picked, and the locks — kept in git. It's the one place your intent lives. Nothing is rendered yet.

RENDERF2 · render variant

Render — frozen, hash-pinned objects

We render the recipe once into the exact Kubernetes objects and freeze that output with a checksum. That frozen output is the render variant. It's never re-rendered — it's what you read before install, what we compare against plain Helm, and what your controller pulls unchanged. The render boundary is the rule: change the object set → a new base (re-render + re-check vs Helm); change only the operating context → no re-render.

RECORDthe proof bundle

Record — what produced it, kept with it

Alongside the render we keep the inputs and the evidence: the recorded inputs (the render intent), content checksums, the Helm-equivalence proof, a security scan, and an install gate. A later reviewer — or an agent — can see exactly what was rendered, from what, and re-run the same check.

ROUTEF3 · prerequisites & routes

Route — the work Helm leaves at the edges

Anything that doesn't survive a config-only render — hooks, CRDs, webhooks, generated facts, target prerequisites, setup jobs — becomes a named route, not hidden engine behaviour. Each route is observed, routed, marked target-specific, or refused. The reason this matters, in the doctrine's words: render config-only and say nothing about where those behaviours went, and the user is more lost than with Helm, not less.

CHANGEF4 · derived variant

Change — customise after install, keep it on upgrade

A derived variant is a copy of a base where you set the operating context — target, region, labels, approvals — or edit any field. Make one per environment from a single base; the next upgrade keeps your edits instead of wiping them. This is the part Helm structurally can't do.

The three kinds of variant

KindWhat it isRe-renders Helm?Lives in
Base variantA reviewed install shape (default, no-crds, ha…). Changing what gets installed means a new base.Yes — and it's checked against Helmthe recipe

4 · The decisions, and why

We chose to……because
Keep config fully rendered (not templated)So you can change any field after install and the change survives upgrades. And the proof is the desired config itself, not a side effect of running an engine.
Freeze the render instead of re-renderingWhat you read is exactly what installs and what your controller delivers — no re-render drift between review and runtime.
Name every route (hooks, CRDs, prereqs)Every behaviour Helm did imperatively still has to happen somewhere — or be deliberately skipped. If we hid that, you'd be more lost than with Helm.
Mark routes automatic: false until earnedNothing is called automatic until the product actually runs the route and committed evidence proves it. No claim ahead of proof.
Report an honest disposition (synced ≠ working)GitOps can say "Synced" while the workload is broken. Separate lanes make the real problems explicit instead of hiding them behind one green tick.
Offer existing-secret basesA default that ships a generated password installs green but breaks silently over GitOps (the pod can't find the Secret while Argo still says Synced). Bring-your-own is the safe path.

5 · Recommended patterns

Take the smallest path that does the job, and grow only when you need to:

You want to…Recommended path
Just see the objectsRender and read them — no account, no cluster.
Install one chartStart at the chart's default base: cub installer setup --pull <package> --base default.
Run a database / anything with a passwordUse the existing-secret base and supply the Secret yourself — don't ship a generated one over GitOps.
Change something after installMake a derived variant — it keeps your change through upgrades, no re-render.
Run dev / staging / prodOne base → many derived variants (per environment, region, customer). The base stays single; the instances live in ConfigHub.
Already run Argo or FluxKeep your controller. Publish once to OCI; point Argo/Flux at the same bundle.

6 · What's yours to decide

Some choices we can't make for you — they depend on your cluster, your secrets, your policy. We surface them clearly and recommend a default, but the call is yours. We guide; you decide.

Which base fits. We recommend default, but you know whether you need ha, no-crds, or existing-secret. The catalog names the trade-off; you pick.

Namespace. Simple charts honour --namespace. Some complex charts embed a namespace in their objects and must install at their canonical one — the chart page says which.

Image pinning. Some default bases ship a floating tag. For reproducible, digest-bound delivery, pin it: --set-image NAME=repo/img@sha256:….

Secrets. Bring your own via the existing-secret base and stage it out-of-band (ExternalSecrets, Vault, or kubectl). We can't invent your production secret.

Prerequisites & target facts. Some bases need a Secret, a CRD, a namespace, or a cluster value to exist first. Stage them before applying, or choose a base that includes them — each one is listed, not assumed.

When to go back to Helm. If a chart isn't in the catalog, plain cub helm template / cub helm install is the right one-shot — just record the inputs (chart, version, values, namespace) so the next upgrade is reproducible.

7 · How verification works

Every chart-variant carries a proof bundle — the receipts that back each claim:

ReceiptWhat it proves
render-receiptThe exact inputs and the checksum of the rendered object set — and that two local renders matched (deterministicAcrossTwoLocalRenders: true).
helm-equivalence-receiptThe cub render equals plain helm template, object for object, after declared normalizations.
scan-receiptA security scan of the rendered objects, with findings by severity.
install-gateA checksum-bound decision on where it's safe to install (local-test / review / production).
object-inventory · variant-revisionEvery object's identity, and the digest chain (recipe → variant → values → renderer → rendered objects).

The model has three moves — render → record → route: render the objects, record the inputs and evidence with them, and route everything Helm leaves at the edges. Live results are reported as a disposition, per lane, per variant — never one blanket tick:

961pass
116watch
124blocked
87not yet run
1484not applicable

watch isn't pass; blocked isn't hidden; not-applicable is counted on its own. And you can check any of it three ways:

Way to checkNeeds a cluster?What it confirms
Run the render check yourself (npm run <chart>:verify-install:render)NoYour own render matches the catalog's recorded contract.
Re-verify the committed evidence (npm run verify)NoThe receipts, hashes, and generated files are self-consistent.
Run a fresh live lane (npm run kind-parity:run / live-parity:run)YesHelm vs cub, and OCI→Argo/Flux, on a throwaway cluster.

8 · What's idempotent, what's deterministic — and why

This is the line that matters most for trusting the catalog: some steps are pure computation you can reproduce offline; others touch a live cluster and can't be byte-identical. We're explicit about which is which.

StageIdempotent?Reproducible from source, no cluster?Why
Render (recipe → objects)yesyes — byte-identicalkustomize over the frozen upstream with pinned inputs; same inputs always give the same objects.
Record (receipts, checksums)yesyesJust hashing and writing committed content — no live state.
Catalog / matrix / site viewsyesyesRe-derived from the committed recipes; stable joins, stable order.
Route (hooks / CRDs / prereqs)plan: yesplan: yes · run: noNaming and classifying is pure; running a route touches a cluster and may have side effects.
Apply (kubectl / Argo / Flux)yes — apply + prune convergesnoDeclarative apply converges to the same state, but it's a live action on a cluster.
Live proof / dispositionnono — not byte-deterministicIt observes a real cluster: pod scheduling, image pulls, controller timing. Each run is a new, point-in-time observation.

So a rename or a re-derivation regenerates offline from committed source; a fresh live result needs a cluster. The doctrine keeps live runs honest: they're serial and ephemeral — cub-lk is kind under the hood, one rig at a time, torn down after; render parity ≠ live-ready, and watch ≠ pass.

9 · Delivery: one source, no surprises

The frozen render is published once to an OCI registry. Argo, Flux, or kubectl all pull the same files — the controller never rebuilds its own version from values. Keep your controller; just point it at the ConfigHub bundle.

# Argo CD Application source
source:
  repoURL: oci://oci.hub.confighub.com:443/target/<space>/oci
  path: ./<space>

# Flux source
apiVersion: source.toolkit.fluxcd.io/v1
kind: OCIRepository
spec:
  url: oci://oci.hub.confighub.com:443/target/<space>/oci

Argo-from-OCI is proven with committed end-to-end receipts. Flux-from-OCI is documented and still in progress until it has the same receipts.

10 · Letting AI make the changes, safely

AI is the fastest way to make a change after install — and the most dangerous if you can't see what it did. Because the config is just files, an agent edits the actual rendered files, and you check before anything ships: the exact diff, a scan for secrets and bad settings, an approval step. If a bad value gets through, you can undo it later — the change is tracked, not lost. The AI proposes; you review and approve; the cluster only sees what passed.
