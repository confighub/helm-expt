How it works

Helm rebuilds your whole config from templates every time, so any change you made by hand is wiped on the next upgrade. We do it differently: render the chart once into plain files, let you change anything afterward, and put your change back on every upgrade. That's why you can change things after you install — and it's the thing Helm can't do.

The core idea

Helm: rebuilt from templates

  • Every setting has to be wired into the template up front.
  • Need a setting the chart didn't expose? You're stuck, or you copy the whole chart.
  • helm upgrade rebuilds from the templates and overwrites what you changed.

Us: kept as files you can edit

  • Render once to plain YAML files you can read.
  • Change any field afterward — by hand, a script, or an AI agent.
  • The next upgrade keeps your change instead of wiping it.

The four stages, F1 → F4

A chart becomes something you can preview, change, and run in four stages. Each is checked on its own, and we publish the honest result — pass, watch, or blocked.

F1 · SOURCE

The chart you pick

The upstream Helm chart and version, pinned. It's the starting point — you pick a reviewed base next.

F2 · BASES & THEIR SAVED RENDERS our render variants

Reviewed install shapes, each rendered and saved

Each chart comes with a few reviewed base variants — named install shapes (default, no-crds, existing-secret, ha, …), each one producing a different set of objects. We render each base once to its exact Kubernetes files, check they match plain Helm, and save that output with a checksum — that saved output is the render variant. (The base is the shape; the render variant is what it produced.) We also record the inputs behind it — chart version, values, namespace — so you or an agent can compare, scan, and re-run it later. That saved render is what you read before install, what we compare against Helm, and what your controller pulls unchanged. A plain installer renders fresh every time; we keep the rendered result.

F3 · WHAT IT NEEDS + THE WORK HELM HIDES

Prerequisites, hooks, and CRDs — named, not hidden

Helm leaves two hard things around the edges. Things the cluster must already have — a Secret, a namespace, a value from the target. And work Helm runs quietly: post-install Job hooks, CRDs that have to exist before the resources that use them, webhook certificates, and setup jobs.

We turn each one into a named step — we watch it, run it, and record what happened — and we prove it actually runs under Argo (PostSync), Flux, and plain kubectl, not just that the YAML was written. Nothing is called automatic until it has earned that (automatic: 0/25). If a hook or CRD isn't handled yet, we show it as a named blocker — never a hidden gap.

F4 · YOUR CHANGES the part Helm can't

Change after install — and keep it

Now you change things and they stay. A derived variant is a copy of a base where you set things like the target, region, labels, and approvals — or edit any field. Make one per environment — dev, staging, prod, per region, per customer — from a single base, and the next upgrade keeps your edits instead of wiping them. Free, the settings and image swaps you choose are kept; with an account, any line you edit is kept.

Letting AI make the changes, safely

AI is the fastest way to make a change after install — and the most dangerous if you can't see what it did. Because the config is just files, an agent edits the actual rendered files, and you get to check before anything ships: the exact diff, a scan for secrets and bad settings, and an approval step. If a bad value gets through, you can undo it later — the change is tracked, not lost. The AI proposes; you review and approve; the cluster only sees what passed.

Delivery: one source, no surprises

The saved render from F2 is published once to an OCI registry. Argo, Flux, or kubectl all pull the same files — the controller never rebuilds its own version from values. Keep your controller; just point it at the ConfigHub bundle instead.

# Argo CD Application source
source:
  repoURL: oci://oci.hub.confighub.com:443/target/<space>/oci
  path: ./<space>

# Flux source
apiVersion: source.toolkit.fluxcd.io/v1
kind: OCIRepository
spec:
  url: oci://oci.hub.confighub.com:443/target/<space>/oci

Argo-from-OCI is proven with committed end-to-end receipts. Flux-from-OCI is documented and still in progress until we have the same receipts.

Three first-run rough edges we handle (not hidden as wins)

When cub applies directly (no controller), these are the things to handle before cub feels better than plain Helm:

  • Change settings with declared inputs or a base edit, not --set. cub rejects Helm flags instead of quietly swallowing a typo. Use --input, --set-image, or edit a base.
  • Upgrades have to remove deleted objects. Plain kubectl apply leaves orphans behind; the managed cub applier removes them, or let Argo/Flux do it.
  • Conflicts need a readable choice. If you edited something live, a re-apply can conflict; the managed applier explains the choice in plain words instead of a raw Kubernetes error.
