How it works: configuration as data

Helm rebuilds your whole configuration from templates every time, so any change you made by hand is wiped on the next upgrade. We do it differently: render the chart once, let you change anything afterward, and put your change back on every upgrade. That's why you can customize after you install — and it's the thing Helm can't do.

The core idea

Helm — configuration as code

  • Every field must be parameterized in the template up front.
  • Need a field the chart didn't expose? You're stuck, or you fork.
  • helm upgrade re-renders from templates and overwrites what you changed.

This — configuration as data

  • Render once to plain, fully-resolved YAML, captured and pinned.
  • Change any field afterward — by hand, a function, or an AI agent.
  • The next upgrade keeps your change instead of wiping it.

The four stages, F1 → F4

A chart becomes something you can preview, change, and operate in four stages. Each is checked on its own, and the honest result — pass, watch, or blocked — is published.

F1 · SOURCE

The chart you pick

The upstream Helm chart and version, locked. A starting point, not yet an installable package — you choose a reviewed base next.

F2 · BASES & THEIR PINNED RENDERS our render variants

Reviewed install shapes, each captured and pinned

Each chart gets a few reviewed base variants — named install shapes (default, no-crds, existing-secret, ha, …), each a different object set. We render every base once to its exact Kubernetes objects, prove they match plain Helm, and store that output as a hash-pinned render variant: the base is the shape, the render variant is the captured result. A generated render intent records the compact config behind it — chart version, values profile, namespace, capability profile, source lock — so people and agents have something durable to compare, scan, promote, and audit. The captured render is what you read before install, what we byte-compare to Helm, and what your controller pulls unchanged at delivery. This is where we go past a plain installer: the output is captured, not re-derived.

F3 · WHAT IT NEEDS + THE WORK HELM HIDES

Prerequisites, hooks, and CRDs — named, not silent

Helm leaves two hard things around the edges. Prerequisites the cluster must already provide — a Secret, a namespace, a target fact. And lifecycle work Helm fires silently: post-install Job hooks, CRDs that must exist before the resources that use them (CRD-first ordering), admission-webhook certificates, and setup jobs.

We make each one an explicit route — observed, then executed, with a receipt — and we prove it actually runs under Argo (PostSync), Flux, and plain kubectl, not just that the YAML was emitted. Nothing is marked automatic until that's earned (automatic: 0/25). Where a hook or CRD isn't handled yet it shows as a named blocker — never a silent gap.

F4 · YOUR CUSTOMIZATIONS the part Helm can't

Change after install — and keep it

Now you change things and they stay. A derived variant is a copy of a base where you set the operating context (target, region, labels, approvals) or edit any field. Make one per environment — dev, staging, prod, per region, per customer — from a single base, and the next upgrade keeps your edits instead of wiping them. Free, the settings and image swaps you set are kept; with an account, any line you edit is kept.

AI-assisted changes, with control

AI is the fastest way to make an F4 change — and the most dangerous if you can't see what it did. Because the configuration is data, an agent edits the exact rendered objects, and you get the safety rails before anything ships: the precise object diff, a scan for secrets and misconfig, gates, and an approval record. If a bad value reaches the cluster, you unwind it after rollout — the change is tracked, not lost. AI proposes; you see and approve; the cluster only sees what passed.

Delivery: one transport, no rerender drift

The pinned render from F2 is published once as an OCI artifact. Argo, Flux, or kubectl all pull the same bytes — the controller never rebuilds a lookalike from values at sync. Keep your controller; just change the source to the ConfigHub OCI bundle.

# Argo CD Application source
source:
  repoURL: oci://oci.hub.confighub.com:443/target/<space>/oci
  path: ./<space>

# Flux source
apiVersion: source.toolkit.fluxcd.io/v1
kind: OCIRepository
spec:
  url: oci://oci.hub.confighub.com:443/target/<space>/oci

Argo-from-OCI has committed end-to-end receipts (proven). Flux-from-OCI is documented and in progress until equivalent receipts are committed.

Observe: an honest disposition, not a green wall

Synced is not the same as working. Live evidence is reported as a disposition — watch is not pass, blocked is not hidden, not-applicable is counted on its own — with what was observed, when, and for which target.

Three first-run caveats we manage (not hidden as wins)

On the no-controller cub-direct path, these are the friction points handled before cub feels better than plain Helm:

  • Customize with declared inputs or a base edit, not --set. cub rejects Helm flags rather than silently absorbing typos. Use --input, --set-image, or edit a base.
  • Upgrades must prune removed objects. Plain kubectl apply leaves orphans; the managed cub-direct applier prunes, or let Argo/Flux do it.
  • Server-side-apply conflicts need a readable choice. A manual live edit can conflict on re-apply; the managed applier surfaces the choice in plain words, not a raw Kubernetes error.
