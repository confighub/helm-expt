Get started in five minutes

On any throwaway cluster: install a chart, change a setting, then upgrade — and watch your change survive. That last part is the thing Helm can't do. No account needed to start.

You'll: pick a chart → see its reviewed render → check what it needs → change it & keep it

1 · Install it — same result as Helm, with a checkpoint

Use a quick dev cluster to compare Helm and cub. Both lanes deliver the same app; the difference is that cub renders to a precise, pinned object set you can read before anything reaches the cluster.

# plain Helm — one step
$ helm install prom prometheus-community/prometheus --version 29.8.0 \
    -n monitoring --create-namespace

# ConfigHub — render the reviewed package, then apply
$ cub installer setup --pull packages/prometheus-community/prometheus/29.8.0 \
    --base default --work-dir ./prom --non-interactive --namespace monitoring
$ kubectl apply -f ./prom/out/manifests

Helm hides one step. cub shows it.

helm install renders the chart and applies it in a single step, so you only see the objects once they're already running. cub does the same work in two visible steps:

1 · RENDER

Read it first

cub installer setup writes the exact objects to ./prom/out/manifests — readable before anything reaches the cluster. It does not re-run Helm; the package already holds the chart's reviewed render.

2 · APPLY

Then install

kubectl apply installs them. Same objects, now running.

$ helm template prom prometheus-community/prometheus --version 29.8.0   # 23 objects
$ ls ./prom/out/manifests   # the same 23, plus cub's explicit Namespace

Same chart, same namespace, same result — Helm-verified, no surprise installs. Parity is the reassurance, not the point. The point is what you do next.

What is --pull packages/…? It points cub at a package — a reviewed chart/version/base whose exact rendered objects are captured and hash-pinned, with recorded inputs, known routes, and proof links. It lives in the public catalog; nothing is downloaded. --pull also takes an oci:// address or a .tgz.

2 · Change it after install — and it stays

Once it's running you'll want to tweak something — more replicas, a different image, a field the chart never let you set. With Helm, the next helm upgrade rebuilds everything from the templates and your tweak is gone, so you redo it every time. cub remembers the change and puts it back when you upgrade.

Free — your settings stay

no account

$ cub installer setup --pull .../prometheus/29.8.0 \
    --set-image server=prom/prometheus:v3.1
# upgrade to a newer chart version
$ cub installer setup --pull .../prometheus/29.9.0
# your image override is carried forward

The options and image swaps you set are remembered, so an upgrade doesn't wipe them.

With an account — any edit stays

account

$ cub installer upload --space my-app
$ edit out/manifests/deployment-server.yaml   # a field no chart value exposes
$ cub installer plan && cub installer upload --yes
# upgrade, merging your hand edit
$ cub installer setup --pull .../29.9.0 --merge-external-source

Change any line in the rendered files — even one the chart never exposed — and the upgrade keeps it.

3 · Catch a classic error first

AI keys, generated passwords, and other Secrets can slip into a rendered chart. On the cub lane they're still files you can inspect, rotate, externalize, or block — before the cluster or registry ever sees them.

apiVersion: v1
kind: Secret
metadata:
  name: ai-provider
stringData:
  AI_API_KEY: sk-prod-old-key-rotate-me   # rotate or externalize
# status: rendered, reviewed — nothing has touched a cluster yet

4 · The other delivery — GitOps via OCI

Already running Argo or Flux from an OCI registry? Skip kubectl. Push the same pinned render to your registry and let the controller you already trust pull it in — it gets the exact reviewed bytes, no re-render.

$ flux push artifact oci://<your-registry>/prometheus:v1 --path=./prom/out \
    --source=cub-render --revision=v1

What we checked

The low-commitment claim: a no-account path reaches the same install outcome, hands reviewed objects to your existing delivery tools, and gives you a correct baseline before you change anything.

Verify the baseline yourself

The npm proof commands are checks against the repo's committed evidence. They're separate from product commands like cub installer setup, helm install, and kubectl apply — use them to confirm the catalog's claims, not to install.

# render contract check (proof, not a product command)
$ npm run redis:verify-install:render -- \
    --base default --work-dir .tmp/demo/redis-default --namespace redis

The Verification page lets you choose between user-side checks, committed-evidence checks, and fresh live lanes.

Get Started is the no-account path. Connected ConfigHub workflows begin when your desired state needs to be shared, reviewed, and managed across a team or a fleet.
