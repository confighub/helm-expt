Check a Helm answer against retained evidence

A capable assistant can render a chart and explain what it sees. This page adds version-specific package records, known limits, and receipts for facts that depend on history or a live run.

For a shorter prompt built around your exact question, start with Check my config. This page keeps the full six-question reference and the benchmark behind it.

New to cub? Install the cub CLI first. Public catalog packages pull and render anonymously, and you sign in only once a command saves or changes ConfigHub data.

The prompt

Copy it whole. Replace the placeholders. Keep secrets out of the values you paste.

I have a Helm chart problem. Chart: <repo/chart@version>. My values: <paste, secrets removed>.

1. Render it exactly as installed: helm template rel <chart> --version <v> -f values.yaml --include-crds
2. List every object it creates. Flag Helm hooks and their phases, lookup() calls,
   admission webhooks, secrets generated at render time, and CRDs shipped or required.
3. For each values key I set, re-render without it and diff. Name every key that changes nothing.
4. Fetch https://confighub.github.io/helm-expt/site/changes.json and check whether this chart
   and version have a checked entry. If they do, open
   https://confighub.github.io/helm-expt/site/charts/index.html?q=<chart> and compare your
   findings against the recorded verdicts. Where you disagree, say why, and prefer the
   receipt to your own guess.
5. If there is no entry, say so, and with my approval file the chart at
   https://github.com/confighub/helm-expt/issues/new?template=problem-chart.yml
   with the chart, version, and everything you found, so it gets a checked entry with receipts.

Steps 1 to 3 run on your laptop and need no account anywhere. Step 4 reads this site's public data. Step 5 files a public GitHub issue, with your approval, using the problem-chart template.

Six questions worth asking

These are what the prompt is really asking, and why each one matters. Where we hold checked evidence, it is linked.

1. What exactly will this install, and what must already exist?

Rendering answers the first half in a minute. The second half, the Secrets, CRDs and namespaces that must be staged first, is where installs actually fail.

Checked evidence: Every catalog entry lists its prerequisites with the packaged configuration; the recorded webhook certificate lifecycle shows the staged-versus-converged evidence per pinned chart.

2. Which of my values keys change nothing?

Helm accepts unknown keys silently, so a typo ships without a warning. Step 3 of the prompt tests every key you set, on your chart, today.

Checked evidence: Our values diagnostics prove the mechanism with digest-identical renders around a deliberate typo.

3. Will this upgrade destroy anything?

Immutable selector changes, renamed resources that orphan state, and changed volumeClaimTemplates surface at apply time, in production, unless somebody diffs the renders first.

Checked evidence: We keep both sides of upgrade pairs committed, for example kube-prometheus-stack 85.3.3 and 87.19.2, so the destructive diff is computable before Friday.

4. What breaks without Helm's lifecycle: hooks, webhooks, CRD ordering?

GitOps applies do not run hooks. Whether the chart still converges is a live question, not a render question.

Checked evidence: The CRD ordering record and the webhook lifecycle evidence answer it per chart, from real runs.

5. Are these the bytes somebody actually reviewed?

What this command does. cub installer is an open-source plugin for the cub CLI. cub installer setup pulls a catalog package and writes its Kubernetes files locally, leaving delivery to kubectl, Argo CD or Flux. The generated scripts stop before doing any work when the plugin or kustomize is missing.

Publishers republish under unchanged version strings; our sweep caught two doing it. This one cannot be answered after the fact, and it cannot be backfilled: every day without a pinned digest is a day you cannot audit later. Start today, with or without us: helm pull plus sha256sum committed to git is a real start; cub installer setup --pull gives you the receipt form.

Checked evidence: The upstream drift record holds both digest pairs from the 2026-08-07 sweep.

6. What ran before, and can I get back to it exactly?

helm rollback re-renders from templates. If you need the recorded revisions you actually ran, they have to exist, and Helm does not keep them.

Checked evidence: The upgrade and rollback proof shows a post-install edit surviving an upgrade and a rollback restoring an exact recorded revision.

Why send us a chart?

A filed chart becomes a checked entry: rendered objects, prerequisites, hooks and CRDs, a flattening verdict, and receipts behind each claim. You get an answer you can verify instead of one you have to trust, and every assistant that reads this catalog afterwards gets ground truth for that chart. The catalog grows from real problems rather than from our guesses.

File a problem chart. Public charts only, and strip secrets from any values you include.

The benchmark behind this page

Two rounds, eighteen questions, one capable assistant raced against our committed receipts. Round one, static chart facts: the assistant scored 96.7% in under a minute per chart, which is why the prompt above trusts it to do the rendering. Round two, questions about time, live state, and history: twelve of eighteen needed records the assistant could not produce, which is why step 4 checks the catalog.

Zero fabricated receipts across both rounds. Two near-misses where confident answers outran the evidence, both documented. The full run data is committed in data/ai-benchmark, so this page's own claims are checkable.

Runs on your laptop: the prompt's render and values checks, and every catalog pull. Needs a ConfigHub account: variants, approvals, and the revision history that makes rollback-to-exact answerable. Needs an account and a cluster: the standing fleet record that binds what should run to what actually reports.

Every checked-evidence link above traces to a committed receipt. When your assistant disagrees with one, we want to hear about that too.
