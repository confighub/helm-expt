How It Works

Generated at: 2026-06-23T08:32:01.928Z UTC · source: committed helm-expt evidence for this how it works guide.

The model is four moves: render, route, deliver, observe. Each move makes a Helm install more visible without pretending every live case is already green.

01

Render

Your chart becomes the same Kubernetes objects, proved object-for-object for the recorded recipe.

02

Route

Hooks, CRDs, target facts, and other quirks become explicit named steps.

03

Deliver

ConfigHub publishes one OCI bundle. Your chosen controller pulls the same bytes.

04

Observe

Receipts show the live result, including watch, blocked, and not-applicable states.

1. Render

Claim: under the same chart, values, base, and capability profile, the cub installer recipe preserves Helm's rendered object set. This proves the recipe, not that the target cluster is ready.

Three adoption caveats we manage

These apply to the cub-direct path for every chart. They are not hidden as proof wins; they are the first-run friction points that must be handled before cub feels better than plain Helm.

CaveatManaged path
Customize with declared inputs or a base edit, not Helm --setcub rejects Helm flags instead of silently absorbing typos. Use --input for declared inputs, --set-image for declared images, or edit/author a base. See Helm to cub migration.
cub-direct upgrades must prune removed objectsPlain kubectl apply leaves orphans. Use the managed cub-direct applier, which prunes, or use Argo/Flux for controller-managed prune.
server-side apply conflicts need a readable choiceA manual live edit can conflict on re-apply. The managed applier surfaces the reconcile choice in plain words instead of letting a raw Kubernetes error be the user experience.

Per-chart password and CRD heads-up: cub adoption caveats.

What Argo or Flux points at

Keep your controller. The practical change is the source: point it at the ConfigHub OCI artifact instead of asking the controller to re-render Helm downstream.

# Argo CD Application source
source:
  repoURL: oci://oci.hub.confighub.com:443/target/<space>/oci
  path: ./<space>

# Flux source
apiVersion: source.toolkit.fluxcd.io/v1
kind: OCIRepository
spec:
  url: oci://oci.hub.confighub.com:443/target/<space>/oci
  secretRef:
    name: confighub-oci-creds

You should see the controller report its normal synced or healthy status after it pulls the same ConfigHub OCI bundle. In this public corpus, Argo-from-OCI has committed receipts; Flux-from-OCI remains in progress until equivalent receipts are committed.
