Try It Now with Kubernetes

Use a quick dev cluster to compare Helm and cub. You can see that both lanes deliver the same app, verify the baseline with npm proof commands, then make changes with a review point before install.

kindany clusterno account
prometheus → monitoring
# plain Helm — one step
$ helm install prom prometheus-community/prometheus --version 29.8.0 \
    -n monitoring --create-namespace

# ConfigHub — render the reviewed package, then apply
$ cub installer setup --pull packages/prometheus-community/prometheus/29.8.0 \
    --base default --work-dir ./prom --non-interactive --namespace monitoring
$ kubectl apply -f ./prom/out/manifests

Same chart, same namespace, same Kubernetes result. cub gives you a checkpoint before the install.

What is --pull?

It points cub at a package: a reviewed chart/version/base with recorded inputs, rendered objects, known routes, and proof links. That is the durable catalog path. It lives here in this repo — nothing is downloaded. --pull also takes an oci:// address or a .tgz.

Helm hides one step. cub shows it.

helm install renders the chart and applies it in a single step, so you only see the objects once they are already running. cub does the same work in two visible steps: render first, then apply.

1 · Render

cub installer setup writes the exact objects to ./prom/out/manifests — readable before anything reaches the cluster. It does not re-run Helm; the package already holds the chart's reviewed render.

2 · Apply

kubectl apply installs them. Same objects, now running.

helm template prom prometheus-community/prometheus --version 29.8.0 # 23 objects → the same, plus cub's explicit Namespace

Same objects, confirmed before you install. Helm-verified. No surprise installs.

Catch a classic error first

AI keys, generated passwords, and other Secrets can slip into a rendered chart. In the cub lane they are still files you can inspect, rotate, externalize, or block before the cluster or registry sees them.

rendered Secret before install
apiVersion: v1
kind: Secret
metadata:
  name: ai-provider
type: Opaque
stringData:
  AI_API_KEY: sk-prod-old-key-rotate-me  # rotate or externalize

# status: rendered, reviewed, not applied

The other delivery — GitOps via OCI

Already running Argo or Flux from an OCI registry? Skip kubectl. Push the same rendered output to your registry and let the controller you already trust pull it in:

prometheus → OCI
$ flux push artifact oci://<your-registry>/prometheus:v1 --path=./prom/out \
    --source=cub-render --revision=v1
