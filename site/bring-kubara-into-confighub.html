For platform teams who run Kubara

Bring a Kubara platform into ConfigHub

Keep Kubara as it is, and approve each change to your platform in ConfigHub. Your first result takes about 15 minutes and needs no account and no cluster.

Give this to your agent“Run cub kubara plan on my Kubara platform, show me what ConfigHub would hold, and change nothing.”

Kubara composes; ConfigHub governs; Argo reconciles. Kubara keeps its catalogs, its generated files and its hub Argo CD. ConfigHub holds a base for each component and a variant for each cluster, with an approval before each release.

The plugin is cub kubara, from confighub/kubara-confighub v0.2.4. Its guide walks every command. This page gives the order, what each step changes, how to undo it, and the evidence.

First result in 15 minutes · Govern it · Check it as a stack · Known limits · Evidence

1. See your platform the way ConfigHub would hold it

This takes about 15 minutes. You need the cub CLI, Kubara v0.15 or newer, and helm. You need no ConfigHub account and no cluster, and nothing changes outside the directories these commands write.

New to cub? Install the cub CLI first. Public catalog packages pull and render anonymously, and you sign in only once a command saves or changes ConfigHub data.

# Install the plugin release this page was checked with
$ cub plugin install confighub/kubara-confighub@v0.2.4

$ cub kubara version

# Optional: Kubara's services, with the Workshop's evidence for each chart
$ cub kubara services

# Write a Kubara config.yaml with a hub in dev and a spoke in prod
$ cub kubara init --out my-platform --services cert-manager,metrics-server,traefik --hub hub-dev:dev --spoke edge-prod:prod

# Copy the env template, then fill in the values it asks for
$ cp my-platform/.env.example my-platform/.env

# Let Kubara generate the platform, as it always does
$ kubara --work-dir my-platform --config-file config.yaml --env-file .env generate --helm

# What ConfigHub would hold: stages, bases, variants and chart evidence
$ cub kubara plan my-platform

# Each service for each cluster, as Kubara's ApplicationSets deliver it
$ cub kubara render my-platform --out my-platform-render

What you get. plan prints the stages in rollout order, a base for each component, and a variant for each cluster that runs it. For each chart it says if the Workshop Catalog checked the exact version Kubara pins. render writes each cluster's services as objects.yaml files, and render.json records each chart, values file and digest.

Already run Kubara? Skip init and kubara generate, and run plan and render on your Kubara work directory.

init, generate and plan take seconds. The first render takes longer, because Helm fetches each chart's dependencies into a cached copy. Your work directory stays as it was. In the render, each Secret keeps its keys and loses its values.

init also writes a .gitignore that leaves out .env, **/charts/, **/Chart.lock and **/*.tgz. If one exists, init adds only the lines it lacks. Keep .env out of Git, because it holds the Argo CD password and your Git token.

To undo, delete my-platform and my-platform-render. The guide explains each step: services, init, plan and render.

2. Govern it: apply, handover, check, handback

These steps bring the platform into a ConfigHub organization and point Kubara's hub at approved releases. apply, handover and handback only write a script. You read the script, then you run it.

Try them on the kind lab first. It builds a Kubara hub and spoke on your laptop, and runs every step below against them. On kind, cert-manager is Degraded and Traefik is Progressing, so check exits non-zero there.

What you need. A ConfigHub organization and cub auth login, with rights to create Spaces, workers and Targets. The hub scripts also need jq, and kubectl access that can write in the hub's argocd and argobot namespaces. The hub needs Argo CD 3.1 or newer; Kubara ships 3.5.

# Render each cluster as Argo CD will, and write apply.sh
$ cub kubara apply my-platform --out my-platform-confighub --capabilities hub-dev=<hub context> --capabilities edge-prod=<prod context>

# Read the script, then run it
$ bash my-platform-confighub/apply.sh

# Write handover.sh; it may approve dev, and prod waits for someone else
$ cub kubara handover my-platform --out my-platform-confighub --capabilities hub-dev=<hub context> --approve-stages dev

# Read the script, then run it against Kubara's hub
$ HUB_CONTEXT=<hub context> bash my-platform-confighub/handover.sh

# Each cluster runs the release its stage approved, and is Healthy
$ cub kubara check my-platform --hub-context <hub context>

# To undo handover, write handback.sh from the directory Git holds
$ cub kubara handback my-platform --out my-platform-confighub --capabilities hub-dev=<hub context> --capabilities edge-prod=<prod context>

$ HUB_CONTEXT=<hub context> bash my-platform-confighub/handback.sh

Pass the same --prefix and --stages to plan, apply, handover, check and handback. Each command refuses a --stages that does not name every stage once, and says which stage is wrong.

On a real platform, pass --capabilities for every cluster. A render that differs from what Argo CD runs makes handover.sh stop on its prune check.

Who approves. By default, handover.sh approves the first release in every stage, as the person who runs it. That first release holds what Git already delivers. To leave a stage to someone else, pass --approve-stages with the stages the script may approve, or none. In the other stages it stops before the hub changes, and prints the approve commands. Once they are run, run handover.sh again. It resumes the same change orders and hands the hub over.

Once a second person approves every change, run apply with --allow-authors=false, then run apply.sh again. After that, handover.sh also stops for that second approval.

If handover.sh stops halfway, fix what it names and run it again. In steps 0 to 4 the hub has not changed. In step 5 some ApplicationSets can read ConfigHub and others Git, so run it again or run handback.sh.

What check judges. A variant passes when one Application reads its latest release from ConfigHub and no Git source. It must also be Healthy, prune nothing, and keep live Secret values. Degraded or Missing fails. Progressing is "not yet": check exits non-zero, records nothing, and you run it again later.

After kubara bootstrap, run handover.sh again. Bootstrap on a handed-over hub silently hands it back to Git, and undoes the changes made in ConfigHub since handover. check then fails each variant with it still lists Git sources. Running handover.sh again is the whole recovery. Do not promote until you have run it.

Before you hand back, put in Git each change you made in ConfigHub since handover. Git undoes any change it does not hold.

To remove the platform from ConfigHub, run handback.sh first, because the hub must not read Spaces you delete. Then list the Spaces with your prefix, check the list, and delete them:

$ cub space list --where "Slug LIKE 'kubara-%'"

$ cub space delete --where "Slug LIKE 'kubara-%'" --recursive-force

After handover

Change a base once, then take the change through the stages with cub changeorder create, cub variant promote, cub variant approve and cub release publish. When Kubara generates something new, such as a newer catalog, run apply and apply.sh again. Each base that changed gets one change order to review, and changes made in ConfigHub stay. To undo a released change, release the state before it with --revision Before:ChangeOrder:<change order>.

The guide has each step: apply, handover, a change after handover, a new Kubara catalog, live status and the Healthy gate, check, handback, what each step changes and if something goes wrong.

3. Check the same platform as a Workshop stack

A Workshop stack is the same platform seen as one composition: a component for each service and a variant for each cluster. Use it to check the platform before anything runs, compose apps onto it, or publish it as OCI. Approvals and handover stay with cub kubara.

cub stack from-kubara runs cub kubara render, so the stack holds the objects Kubara's hub delivers. It needs the Workshop plugin, cub kubara v0.2.4 or later, helm, node and oras, and no account.

# Install the Workshop plugin release this page was checked with
$ cub plugin install confighub/cub-workshop@v0.6.56

# Kubara's own output as one stack
$ cub stack from-kubara my-platform --out my-platform-stack

# Check the whole stack, then what one cluster runs
$ cub stack check my-platform-stack/stack.yaml

$ cub stack check my-platform-stack/stack.yaml --cluster edge-prod

# Publish one OCI index; it checks every cluster before it pushes
$ cub stack publish my-platform-stack/stack.yaml --out oci://<registry>/<repository>:<tag>

check looks for components that conflict, CRD order, served API versions, webhooks that need a certificate, and namespaces. It ends with CHECKED or REFUSED. It is a static check, so it cannot show that a cluster runs the platform. publish refuses before it pushes anything when one cluster does not check out, and attaches each cluster's verdict to the index.

Without --out, from-kubara writes confighub/ inside the work directory. It can suggest cub stack upload --run next. That creates its own Spaces and Components, apart from the ones apply.sh creates, so give it another --space-prefix. Since Workshop v0.6.55 the prefix names each Component <prefix>-<component> as well as its Spaces, so the upload creates no bare Component such as cert-manager. You do not need an upload to govern the platform.

The Workshop README section Turn a Kubara platform into one stack has the details. For a ready-made example, cub stack sandbox kubara-platform prints the Catalog's tested images of the same three charts as Kubernetes YAML. It does not start a cluster.

Need GitOps services and the shop app? Save, change and resume a local platform using the retained kubara-gitops-shop selection. The Guide provides direct cub commands and an assistant task, with saved results and a failure case. Static composition does not establish GitOps reconciliation or application health.

Continue with a managed fleet, or a cluster in minutes

The following commands create or change ConfigHub records. First sign in to the organization you intend to use, inspect the fleet manifest, and confirm the demo Space names are available. They use the shipped fleet manifest, not the files generated above.

$ cub fleet up demo-platform

$ cub fleet age demo-platform && cub fleet status demo-platform

$ cub variant promote metrics-server-demo-dev --dry-run

If a remote step fails, inspect the records already created before retrying. Preserve existing resources; use the linked runbook for scoped cleanup.

cub cluster up --name demo --space demo-cluster

One command creates a temporary kind cluster, installs Argo CD, and wires it to a ConfigHub Space. It needs a ConfigHub account and Docker; the cluster runs on your laptop.

The composition, as evidence

Each component in a stack carries a certified-bundle receipt that names what it is and how it may be flattened, and the eight-bundle EKS inference platform is one worked example. The single composition verdict over a whole stack is specified and runs two ways today. This repository arms it as a regression gate over its own receipts. The workshop plugin's cub stack check runs it anywhere, refusing a real conflict rather than reporting one. As a gate inside the ConfigHub product it remains proposed.

4. Known limits

Read these before you run apply.sh or handover.sh on a real hub. The guide keeps the full list.

  • It has run on kind only. The kind lab ran it with Kubara v0.15.0 and v0.16.0, and Argo CD 3.5.2. It has not run on a production platform.
  • The Healthy gate can read stale health. argobot writes each Application's sync and health to its variant Space, and the gate reads that status. The status is not yet tied to the Release, so for a few minutes after a release the gate reads the previous release's health. Run cub kubara check on the stage ahead before you promote.
  • argobot cannot refresh Kubara's Applications (confighub/argobot#13). It looks for an Application named after the Space, and Kubara names them <cluster>-<service>. A release reaches the cluster on Argo CD's next poll, within about three minutes.
  • An Argo CD self-upgrade through ConfigHub is not proven. On kind, the hub's argocd Application never finishes a sync, because its Ingress gets no address. In the Kubara v0.16 run, the argo-cd release to dev did not land.
  • kubara bootstrap on a handed-over hub hands it back to Git. It says nothing about ConfigHub. Run handover.sh again straight after it.
  • A cluster that joins later gets its Secrets without values. Your secret store must fill them.
  • The example index checks only the offline steps. In Workshop v0.6.56, cub config examples returns the kind lab first for "bring my Kubara platform into ConfigHub". Its entry ran init, generate and plan with the released plugin. It did not run the connected, controller or runtime steps, and points to the lab's logs for them. Maintainer review of the entry is pending.

6. Give your agent this prompt

I run a Kubara platform. Its work directory is <path>.

1. Install cub kubara v0.2.4 with: cub plugin install confighub/kubara-confighub@v0.2.4
   Then read https://github.com/confighub/kubara-confighub/blob/main/docs/user/cub-kubara.md
2. Run cub kubara plan and cub kubara render --out <new directory> on my work directory.
   Tell me the stages, the bases and variants, and which charts the Workshop Catalog
   checked at the exact version Kubara pins. Change nothing.
3. Run cub kubara apply and cub kubara handover with --out <new directory>.
   Tell me what apply.sh and handover.sh would change. Do not run either script.
4. List the guide's known limits that apply to my platform.
5. For each chart the plan marks unchecked, say so, and with my approval file it at
   https://github.com/confighub/helm-expt/issues/new?template=problem-chart.yml

Steps 1 to 4 read your files and write new directories only. Step 5 files a public issue with your approval, so an unchecked chart can get a Catalog entry with receipts.

Why hand any of this to an agent? Our committed two-round benchmark measured where agents are already strong and where they cannot be. A bare agent with a shell answered static chart questions at 96.7 percent. Twelve of eighteen questions about time, live state, and accountability needed records the agent could not produce. The toolchain carries day one; the records carry every day after. The benchmark and the full prompt live on the challenge page, and the run data is committed in data/ai-benchmark.

Make latest discoverable, not deployable: the adapted lane's mechanism

The adapted lane keeps targetRevision: latest as a discovery address but leaves automated sync off. On the automated path, mutable latest cannot race past approval, promotion, or rollback, and ConfigHub selects the exact OCI digest before Argo CD receives it. Blocking a privileged human or a manual Argo sync needs your own RBAC or admission control.

The adapted lane retains targetRevision: latest as the ConfigHub OCI discovery address, but leaves spec.syncPolicy.automated absent from every managed Application. Pinned argobot v0.1.6 runs with ARGO_SYNC_MODE=kubernetes, ARGO_NAMESPACE=argocd, and ARGO_REFRESH_TYPE=hard, so it refreshes but cannot deploy.

ConfigHub revalidates the authoritative release and submits operation.sync.revision=<ManifestDigest> with Kubernetes UID/resourceVersion compare-and-set only when no Argo operation is active. This is the governed improvement: mutable latest cannot race past approval, promotion, or rollback, while Argo remains the local reconciler.

The authority check inventories Applications across the whole cluster: all managed Applications must live in argocd, and the adapted lane permits zero ApplicationSets. Retained release-N Tags expose contiguous history, but the exact OCI ManifestDigest remains deployment authority. Client opening and closing checks plus the no-auto fence stop a rejected raced Release from deploying through this managed path. Atomic rejection of the Release record requires server-side publish preconditions.

Production approval uses the Unit slug and server HeadRevisionNum. Authoritative reads before and after must preserve the Unit ID, observed numeric head, and DataHash, and the gate must clear exactly once.
