Before and after

See what an Argo CD app of apps becomes

Argo CD keeps syncing. ConfigHub holds a base and a variant for each app, and each Application changes only its source, from a path in Git to a ConfigHub release.

What you need. git and cub with the argo plugin. No account and no cluster.

1. See what you have today

The example is an app of apps in confighub/examples. One root Application syncs two child Applications, and each child syncs one environment from Git.

FileWhat it is
apps/apptique-dev.yamlan Application that syncs one environment's manifests from Git
apps/apptique-prod.yamlan Application that syncs one environment's manifests from Git
manifests/apptique/dev/deployment.yamlthe Deployment that Application syncs
manifests/apptique/prod/deployment.yamlthe Deployment that Application syncs
root/root-app.yamlthe root Application, applied by hand, which syncs the apps directory

2. See what ConfigHub would hold

The plan reads the files and says what ConfigHub would hold. It runs nothing and changes no cluster.

3. See what changes in each Application

After the handover each child Application reads a ConfigHub release instead of Git. These are the only fields that change.

ApplicationFieldBeforeAfter
apptique-devspec.source.pathgitops/argo/beginner-app-of-apps/manifests/apptique/dev.
apptique-devspec.source.repoURLhttps://github.com/confighub/examples.gitoci://<gateway>/space/argo-apptique-dev-in-cluster
apptique-devspec.source.targetRevisionmainlatest
apptique-prodspec.source.pathgitops/argo/beginner-app-of-apps/manifests/apptique/prod.
apptique-prodspec.source.repoURLhttps://github.com/confighub/examples.gitoci://<gateway>/space/argo-apptique-prod-in-cluster
apptique-prodspec.source.targetRevisionmainlatest

The finalizer, the sync policy and the destination stay as they are. <gateway> is the OCI address your ConfigHub serves releases from.

The root Application apptique-apps also changes only its source. It moves to the Space argo-apptique-apps-children, which holds the two child Applications, as step 2 of the handover says.

4. Try it yourself, with no account

Install cub and the argo plugin as Bring your Argo CD apps into ConfigHub shows, first.

# fetch the example at the commit this page was built from
$ git clone https://github.com/confighub/examples.git && git -C examples checkout 7f1b8f2fc849bb6488bc2c58f1469172018fc9dd

$ cd examples/gitops/argo/beginner-app-of-apps

# read the plan; it runs nothing
$ cub argo plan .

# write the Applications before and after, and the scripts, to onboard/
$ cub argo apply . --out onboard

Compare onboard/control/ with onboard/repointed/ to see the table above for yourself.

See it live in ConfigHub

Everything above runs on your own machine with no account. To see the same example in ConfigHub, load it into your own organization with the commands below.

With your own account

# sign in to your organization
$ cub auth login

# fill ConfigHub with the bases and variants the plan names; it changes no cluster
$ bash onboard/apply.sh

apply.sh also needs kustomize. onboard/cleanup.sh takes everything back out. The handover, which moves Argo CD onto ConfigHub releases, is a separate step in the Argo CD Guide.

5. Technical notes and disclaimers

  • The plan ran on 2026-10-25 with cub v0.9.0 and argo plugin 0.3.2, inside a checkout of the example. The recorded files and their receipt hold every input and output.
  • An oci:// source needs Argo CD v3.1 or newer. The plan checks this before the handover.
  • Never delete these Applications to undo the handover. Their finalizer deletes everything they deployed.
