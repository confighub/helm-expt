1. Choose the question and command

First decide which answer you need

Inspection, materialization, destination checks, and post-deployment checks use different inputs. A result from one stage does not pass the next stage.

QuestionMinimum inputDeployment needed?
What do I have?The source, package, snapshot, or files to inspect.No
What will it produce?Source inputs plus its native tool, or literal objects where this step is a no-op.No
Can this destination accept it?The exact candidate plus current destination facts.No
Did it work?The exact delivered revision plus the live evidence required by the claim.Yes

Keep evidence state separate from result state. For example, an AICR resource check cannot run when the selected components were never deployed. That stage is blocked or not run; it is not a failed GPU or configuration result.

2. Tell product commands from project checks

Product commands

cub, helm, kubectl, Argo, and Flux render, install, deliver, or manage configuration.

Project checks

npm run ... checks this repository's generated files, receipts, and summaries, among other records.

Complete project check

npm run verify checks the whole repository. Use it before publishing or reviewing a large change.

3. See what render, record, and route mean

The Kubernetes YAML shows what would run. The source record explains how it was produced. Lifecycle records explain work such as hooks, CRDs, Secrets, and setup jobs.

MoveMeaningWhat gets checked
RenderTurn the chart and its recorded settings into the exact Kubernetes objects.The object set matches the expected Helm result.
RecordKeep the source, settings, objects, diffs, checks, and receipts together.A reviewer can explain the result and repeat the check.
RouteState how hooks, CRDs, Secrets, setup jobs, target requirements, and GitOps delivery are handled.Required work is assigned, tested, blocked, or marked as not yet run.

4. Choose saved evidence or a fresh run

Saved evidence

Already in the repository. Use it to review a claim and confirm that summaries still match their receipts and data.

Fresh evidence

Created by a new run. It may create kind clusters, use ConfigHub, publish OCI artifacts, wait for Argo or Flux, and write receipts.

Run live checks one at a time

Do not overlap fresh live checks. Keep clusters, credentials, and receipts separate.
