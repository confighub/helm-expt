Live walk: kai-scheduler's install hooks on a throwaway cluster, 2026-10-11

This log records two runs. The chart kai-scheduler v0.16.9 has two hook phases that Helm runs around an install. The site's test script for its default base did not run them, and said so. The first run shows what that left on the cluster and what the hooks then did by hand. The second run shows the script after it was changed to carry the hooks out itself. You can also view this as a markdown file.

UNOFFICIAL/EXPERIMENTAL

This is a dated record. It is not a Guide. Every line that starts with $ is a command that was run, and the text under it is the output it printed. Times are UTC. A line longer than 220 characters is cut and ends with ....

Versions and setting

  • cub v0.8.7 with the installer plugin, in a home directory that holds no ConfigHub credentials. No account was used.
  • kind v0.31.0 with a node at Kubernetes v1.35.0, kubectl client v1.36.0, kustomize v5.8.1, Docker 29.4.0.
  • Each run had its own new cluster with one node and its own kubeconfig file. The machine's default kubeconfig was not touched.
  • The scripts ran under the system's bash 3.2.
  • The scratch directory is written <work>.

Run 2. The changed script

The script generator was changed after run 1. For an install hook that the package ships and the plan assigns to the delivery workflow, the script now applies the hook's objects in Helm's hook-weight order, waits for each Job, and deletes the hook objects. Pre-install hooks run before the rendered objects and post-install hooks after them.

This run used a new cluster. Lines that end condition met or serverside-applied are filtered out of the script's output.
