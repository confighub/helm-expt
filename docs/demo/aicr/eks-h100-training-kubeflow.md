# AICR EKS H100 training example

This example starts from NVIDIA AICR v0.14.0 and asks for an EKS platform with H100
accelerators, Ubuntu, Kubeflow, and a training workload. AICR turns those criteria into
a versioned recipe, then generates a Flux bundle with the components in dependency
order.

The example exists to show how an AICR package can enter the same ConfigHub path as a
Helm catalog entry. ConfigHub does not replace the AICR recipe. It records the recipe,
the generated configuration, the remaining install-time choices, and the environment
variants that should run it.

## What is committed

- [aicr.yaml](../../../examples/aicr/eks-h100-training-kubeflow/aicr.yaml) is the
  `AICRConfig` that describes the recipe and bundle commands.
- [recipe.yaml](../../../examples/aicr/eks-h100-training-kubeflow/recipe.yaml) is the
  generated component recipe.
- [flux-bundle](../../../examples/aicr/eks-h100-training-kubeflow/flux-bundle) contains
  the Flux resources generated by AICR.
- [generation-receipt.yaml](../../../examples/aicr/eks-h100-training-kubeflow/generation-receipt.yaml)
  records the AICR version, criteria, options, commands, and current proof boundary.

The bundle fixes the component versions before installation. Four choices remain in
this example: the StorageClass, the selector for accelerated nodes, the selector for
training workloads, and the Git repository that Flux will read. The first three were
supplied to the bundle command. The repository was not, so AICR generated
`https://github.com/YOUR_ORG/YOUR_REPO.git`. The receipt records that placeholder and
marks the bundle as not deployable.

## Rebuild the example

Install AICR v0.14.0, then run these commands from the example directory:

```bash
aicr recipe \
  --service eks \
  --accelerator h100 \
  --os ubuntu \
  --intent training \
  --platform kubeflow \
  --output recipe.yaml

aicr bundle \
  --recipe recipe.yaml \
  --deployer flux \
  --output flux-bundle \
  --storage-class gp3 \
  --accelerated-node-selector nvidia.com/gpu.present=true \
  --workload-selector app.kubernetes.io/part-of=training
```

That command reproduces the committed bundle. For a usable bundle, add
`--repo https://github.com/ORG/REPOSITORY.git`, regenerate it, and review the resulting
GitRepository and HelmRelease objects before upload.

Run `npm run aicr-example:verify` to check the committed criteria, command options, and
every checksum in the generated bundle. The verifier also checks that the repository
placeholder remains visible and that the receipt does not call this bundle deployable.

## Create a ConfigHub base variant

The next complete lane packages the literal Flux YAML as one OCI artifact and uploads
it:

```bash
cub variant upload \
  --component aicr-eks-h100-training-kubeflow \
  --variant base \
  --granularity per-file \
  oci://REGISTRY/aicr-eks-h100-training-kubeflow:v0.14.0
```

`cub variant upload` records the source reference and resolved digest on the Space.
After upload, development, staging, production, region, or cluster-class differences
belong in derived variants.

This repo does not yet claim that upload or a live GPU-cluster reconciliation passed.
The generated repository placeholder must also be replaced. Until those steps and
receipts are complete, the AICR pathway is partial.
